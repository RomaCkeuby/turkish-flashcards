# Roadmap: независимый сайт и аккаунты на домашнем сервере

> Обновление 3 ноября 2026: новое направление описано в [ROADMAP-SUPABASE.md](ROADMAP-SUPABASE.md).
> Дальнейшие этапы аккаунтов на домашнем сервере ниже — исторический план.
> Реализованные гостевой режим и публичная подборка используются в новой архитектуре.

Статус: план, реализация не начата. Дата: 2 ноября 2026 года.

## Целевой результат и границы первой версии

- Постоянный сайт содержит интерфейс и публичную базовую подборку. Открывается впервые с интернетом даже при выключенном ПК.
- Гость тренируется по перемешанной колоде без записи в аккаунт. Доступны оба направления, фильтры, переводы и примеры.
- При доступном сервере пользователь создаёт аккаунт по приглашению, входит и занимается по индивидуальному расписанию. Аккаунты, сессии и прогресс хранятся в SQLite на ПК.
- При недоступном сервере регистрация, вход и сохранение прогресса аккаунта недоступны; свободная тренировка остаётся доступной.
- Коллекция в первой версии общая. Импорт, редактирование, обновление, удаление и слияние доступны владельцу. Обычные пользователи читают коллекцию и меняют только свой прогресс.
- После предварительного сохранения сайта возможна свободная тренировка без интернета. Сохранение может быть удалено браузером; при отсутствии ресурсов приложение объясняет, что нужна загрузка с интернетом.
- Гостевые ответы не импортируются в аккаунт. Фоновая отправка офлайн-ответов и отдельные личные коллекции относятся к следующим версиям.

## Что уже есть в проекте

- `apps/web/src/api.ts`: единая точка серверных запросов; база для отделения гостевого источника от серверного.
- `apps/web/src/pages`: готовые экраны занятий, словаря, статистики и настроек.
- `apps/server/src/database.ts`: SQLite, очередь, история, отмена оценки, изменения коллекции. Сейчас нет разделения по пользователям.
- `apps/server/src/hosting.ts`: общий HTTP Basic, запрет внешних записывающих запросов и CORS только для разработки. Для отдельного сайта этого недостаточно.
- `apps/server/update-packages/current`: подготовленный пакет на 600 записей; его можно использовать как вход для публичной подборки.
- `PLAN.md`: существующий план. Этот roadmap дополняет его. Сохраняется принцип: внедрять и проверять один законченный подэтап за раз.

## Архитектура

```text
Постоянный HTTPS-сайт
  ├─ интерфейс + версионированная публичная подборка
  ├─ браузер: перемешанная колода, настройки, кэш
  └─ по явному подключению: HTTPS API через туннель
       └─ сервер на ПК → SQLite: пользователи, сессии, личный прогресс
```

Гостевые идентификаторы происходят из стабильных ключей пакета, а не из номеров строк SQLite. При переходе в аккаунт сервер создаёт свою учебную очередь; текущая гостевая карточка автоматически не оценивается на сервере.

## Роли агентов

Роли — назначения для будущих запусков, а не постоянно работающие агенты. Один агент может последовательно выполнять несколько задач своей роли.

| Роль | Ответственность | Основная область |
| --- | --- | --- |
| Координатор | Контракты, зависимости, интеграция, выпуск и контроль границ | общие договорённости, конфигурация, документация |
| Агент данных и сервера | Экспорт подборки, миграции, аккаунты, прогресс и серверная авторизация | `apps/server`, скрипты экспорта |
| Агент интерфейса | Источники данных, гостевое занятие, вход, состояния соединения | `apps/web/src` |
| Агент проверки и доставки | Регрессии, проверка двух пользователей, PWA, сборка и публикация | тесты, статические ресурсы, конфигурация доставки |

Максимум одновременно: координатор и три исполнителя. Два агента не меняют один файл одновременно; при пересечении работа идёт последовательно. Проверяющий сначала пишет сценарии и отчёт, затем исправления назначаются владельцу области. Учётные данные и приватные данные не передаются в публичную сборку.

## Этап 0. Зафиксировать контракты и поведение

Ответственный: координатор. Проверка: агент сервера и агент интерфейса.

Задачи:
- Описать форматы публичной карточки, manifest, возможностей сервера, пользователя, сессии и ответа оценки.
- Зафиксировать состояния: гость; подключение; сервер доступен без входа; аккаунт; сервер недоступен; сессия истекла; результат оценки неизвестен.
- Выбрать способ сессии для разных доменов и хранения в браузере. Не рассчитывать на доступность сторонних cookies. Предварительный вариант: непрозрачный отзываемый bearer-токен в памяти, повторный вход после перезагрузки; сервер хранит хеш токена и срок действия.
- Определить границы прав: владелец редактирует общую коллекцию; учащийся работает только со своим прогрессом. Создание аккаунта — по приглашению владельца, при работающем сервере.
- Для постоянного сайта определить базовый путь и маршрутизацию, совместимую с GitHub Pages.
- Зафиксировать измерения: открытие сайта при выключенном ПК, показ перевода, следующая карточка, размер сборки и пакета. Пороговые значения выбрать после исходного замера на целевом телефоне.

Готово, когда: контракты и матрица прав записаны, у каждого состояния есть ожидаемое поведение, неизвестные продуктовые решения имеют явно указанное допущение.

## Этап 1. Независимая подборка и гостевой режим

### 1.1. Публичный пакет карточек

Ответственный: агент данных и сервера. Зависимость: этап 0.

- Создать воспроизводимый экспорт из подготовленного источникового пакета, без чтения личного прогресса и пользовательских исправлений рабочей базы.
- Включить переводы, примеры, направления, фильтры, стабильные ключи, источники и лицензии.
- Добавить версию схемы, версию подборки, количество записей и контрольную сумму.
- Проверять дубли ключей, обязательные поля и отсутствие приватных полей.

Готово, когда: пакет воспроизводится командой и достаточен для автономного чтения словаря и занятия.

### 1.2. Источники данных и свободная тренировка

Ответственный: агент интерфейса. Зависимость: контракт этапа 0; до готовности 1.1 использовать небольшую фикстуру.

- Отделить гостевые операции от текущего серверного API, сохранив серверный режим.
- Убрать обязательные серверные запросы из гостевых экранов главной, словаря, карточки и настроек.
- Добавить перемешивание без повторов до завершения выбранной колоды, смену направления и фильтров.
- Показывать гостевой режим и отсутствие записи ответов в аккаунт.
- Недоступные операции редактора и импорта объяснять через состояние режима; прямой переход по URL тоже должен обрабатываться.

Готово, когда: с полностью остановленным сервером открываются все гостевые экраны, фильтры работают, колода проходится, серверный режим не сломан.

### 1.3. Статическая сборка и маршруты

Ответственный: агент проверки и доставки. Зависимость: этап 0; интеграция после 1.1–1.2.

- Настроить сборку для пути репозитория GitHub Pages и прямые переходы/перезагрузку маршрутов.
- Подготовить конфигурацию публикации и воспроизводимую локальную проверку статической сборки.
- Проверить отсутствие SQLite, паролей, токенов и приватных исправлений в публикуемых файлах.

Готово, когда: сборка работает на статическом хостинге, первая загрузка не требует ПК, обновление страницы внутри словаря не даёт 404.

Рубеж A: независимый сайт со свободной тренировкой. Уже полезная версия без аккаунтов.

## Этап 2. Аккаунты и отдельный прогресс

### 2.1. Миграция SQLite и права

Ответственный: агент данных и сервера. Зависимость: этап 0.

- Сделать согласованную резервную копию SQLite с учётом WAL, проверить восстановление на копии; простое копирование одного открытого файла БД недостаточно.
- Добавить пользователей, роли, приглашения и сессии.
- Привязать состояние повторений, историю, статистику и отмену ответа к пользователю; ключ состояния — пользователь + карточка.
- Перенести существующий прогресс владельцу ровно один раз; новые аккаунты начинают с пустым прогрессом.
- Проверить все пути чтения и записи, включая детали карточки, слияние, откат, удаление и отключение направлений.
- Общие изменения коллекции сохраняют прогресс всех пользователей по определённым правилам; слияние обрабатывает состояние каждого пользователя.

Готово, когда: два пользователя имеют независимые очереди, оценки, отмены и статистику; доступ к чужим данным исключён сервером; миграция повторно не дублирует данные.

### 2.2. API входа и надёжная запись оценки

Ответственный: агент данных и сервера. Зависимость: 2.1 и контракт этапа 0.

- Реализовать активацию приглашения, вход, выход, проверку и отзыв сессии.
- Использовать хеширование паролей с солью и подходящей вычислительной стоимостью; ограничить частоту попыток входа.
- Проверять роль и пользователя из сессии; не доверять присланному `userId`.
- Согласовать HTTP Basic с API аккаунтов: общий Basic не должен блокировать разрешённые preflight и заменять пользовательскую авторизацию.
- Настроить CORS для точного списка адресов сайта и согласовать правила Origin/CSRF с выбранной авторизацией.
- Добавить идентификатор операции оценки и идемпотентную транзакцию: повтор запроса возвращает результат без второго ответа в истории.
- Сохранить проверку актуальности при отмене ответа, включая параллельные вкладки и устройства одного пользователя.
- Предоставить безопасную информацию о версии и возможностях API для проверки совместимости.

Готово, когда: вход и оценка работают между разными доменами, повтор запроса не удваивает прогресс, истёкшая сессия и неверные права обработаны.

### 2.3. Интерфейс подключения и аккаунта

Ответственный: агент интерфейса. Зависимость: контракт этапа 0; окончательная интеграция после 2.2.

- Добавить адрес HTTPS-сервера, ограниченные по времени проверки соединения и отмену устаревших запросов.
- Перед отправкой пароля явно показывать выбранный сервер. Не перенаправлять сессию на другой адрес автоматически.
- Добавить создание аккаунта по приглашению, вход, выход и имя пользователя.
- Разделить состояния «сервер недоступен», «нужен вход», «нет прав» и «несовместимая версия».
- Личный режим использует существующую серверную очередь и персональные данные; гостевой режим использует опубликованную подборку.
- При выходе/смене аккаунта очищать личные данные в памяти и отменять запросы предыдущего пользователя.

Готово, когда: на одном телефоне можно поочерёдно войти двумя пользователями без показа чужой статистики и пользоваться гостем без входа.

Рубеж B: аккаунты и повторения через ПК; гостевая тренировка работает независимо.

## Этап 3. Обрыв связи и работа без интернета

### 3.1. Обрыв соединения в занятии

Ответственный: агент интерфейса; API-коррекции — агент сервера. Зависимость: этап 2.

- Сохранять текущую карточку при сбое и явно показывать статус отправленной оценки.
- При неизвестном результате повторять ту же операцию с тем же идентификатором; не генерировать новую оценку автоматически.
- Предлагать переход в свободную тренировку без автоматического переноса гостевых ответов в аккаунт.
- При восстановлении связи предлагать вернуться к серверной очереди. Не переключать режим посреди ответа.

Готово, когда: отключение туннеля до отправки, во время отправки и после фиксации ответа не вызывает двойного учёта или ложного сообщения о сохранении.

### 3.2. Кэш сайта и обновления

Ответственный: агент проверки и доставки. Зависимость: рубеж A; интеграция после стабилизации интерфейса.

- Кэшировать интерфейс и публичную подборку через service worker; не кэшировать авторизованные API-ответы, пароли и сессии.
- Добавить manifest установки и понятный статус готовности к работе без интернета.
- Устанавливать новую подборку целиком после проверки; при неудаче сохранять старую рабочую версию.
- Не смешивать несовместимые версии интерфейса и формата пакета; обновление приложения не прерывает занятие.
- Проверить запуск после закрытия браузера, обновление и отсутствие кэша, очистку хранилища, Android и iOS.

Готово, когда: после предварительной загрузки и включения авиарежима сайт заново открывается и позволяет пройти колоду; ошибки кэша объясняются пользователю.

## Этап 4. Проверка и выпуск

Ответственный: координатор. Исполнители: проверяющий и владельцы областей. Зависимость: этапы 1–3.

- Выполнить typecheck, существующие регрессии, новые проверки миграции/аккаунтов/идемпотентности и production build.
- Прогнать матрицу: ПК включён/выключен; туннель доступен/оборван; интернет есть/нет; гость/владелец/два учащихся; вход истёк; две вкладки; повтор оценки; обновление сайта и пакета.
- Проверить на реальном телефоне междоменные запросы через туннель: локальный mock не подтверждает работоспособность этой схемы.
- Сравнить измерения с этапом 0. Гостевой запуск не ждёт тайм-аута ПК; после загрузки колоды переворот и следующая карточка не требуют сети; набор данных не перечитывается целиком на каждый ответ.
- Подготовить инструкции запуска сервера, подключения, приглашения пользователей, резервного копирования и восстановления.
- Выбрать подключение: ручной адрес временного туннеля для первого запуска; постоянный адрес — отдельная настройка, если доступны домен и учётная запись провайдера.
- Подготовить статические файлы и проверить их перед публикацией. Перед миграцией рабочей базы — подтверждённая резервная копия. Выкатывать подэтапами.

Готово, когда: выполнена матрица, существующий прогресс сохранён, миграция проверена на копии и есть инструкция восстановления предыдущей серверной версии вместе с совместимой базой.

## Порядок и параллельная работа

1. Координатор завершает этап 0 и фиксирует контракты.
2. Параллельно: серверный агент делает 1.1; интерфейсный — 1.2; проверяющий — 1.3 и сценарии регрессий.
3. Координатор собирает и принимает рубеж A.
4. Параллельно: серверный агент делает 2.1 → 2.2; интерфейсный — 2.3 на согласованных фикстурах; проверяющий — проверки миграции и разделения пользователей.
5. Координатор принимает рубеж B.
6. Параллельно при непересекающихся файлах: интерфейсный агент делает 3.1; проверяющий — 3.2; серверный закрывает API-дефекты.
7. Этап 4: интеграция, проверка на телефоне, исправления и выпуск.

Назначение задачи агенту должно содержать: ID подэтапа, цель, разрешённые файлы, контракт, зависимости, критерии приёмки и обязательные проверки. Изменение схемы БД и соответствующих серверных функций выполняет один владелец последовательно. Работы над отдельными подэтапами запускаются после приёмки их зависимостей.

## После первой версии

- Персональные подборки и исправления каждого пользователя.
- Локальное хранение расписания и ответов аккаунта с последующей синхронизацией.
- Разрешение конфликтов между устройствами, отменами, удалениями и слияниями.
- Постоянно доступные аккаунты и прогресс во внешнем хранилище.
- Автоматическое обнаружение адреса сервера, если ручное подключение окажется неудобным.

Эти возможности не входят в критерии готовности первой версии и требуют отдельных контрактов и проверок.
