# Cloudflare Pages + Supabase: реализация и запуск пилота

Состояние на 3 ноября 2026: подготовлен код облачного учебного пилота и проверен
локальный перенос снимка SQLite в PostgreSQL. Облачные проекты не созданы,
публичного облачного адреса нет. Это не завершение миграции M8/M9.

Рабочий прогресс продолжает храниться в SQLite. Домашний сервер, туннель и автозапуск
ещё нужны для прежней рабочей версии. Их отключение допустимо только после полного M6–M8.

## Что готово

- `scripts/cloud/snapshot.mjs`: онлайн backup SQLite, integrity/FK checks, экспорт
  версии 1, SHA-256, инвентаризация и стабильные ключи без изменения исходной базы.
- `supabase/migrations`: каталог Base/Override, источники, примеры, теги, история,
  удаления, профили, закрытые роли/снимки, персональные состояния и журналы.
- RPC `cloud_stats`, `cloud_entries`, `cloud_filters`, `cloud_next_card`,
  `cloud_review`, `cloud_undo`; атомарная оценка, per-user advisory lock и идемпотентность.
- Отдельные `local / guest / cloud`, официальный Supabase Auth client, формы входа,
  регистрации и восстановления, обновление сессии и очистка личных черновиков при смене аккаунта.
- Облачный пилот использует существующие главную, занятия и словарь. Административные
  действия скрыты и отклоняются адаптером; localhost API не используется как fallback.
- `scripts/cloud/import.mjs`: offline dry-run и подготовка транзакционного SQL
  с обязательным UUID владельца, защитой от непустого назначения/повторного импорта.
- `cloud:restore-check`: восстановление в изолированный PostgreSQL/PGlite,
  сравнение эффективных значений всего словаря, обеих очередей, статистики и назначения прогресса.
- CI для типов/тестов/сборки, отдельный job Supabase CLI reset/lint/pgTAP.
  CI не публикует сборку с фиктивными настройками и не получает личную базу.

## Локальные команды

Из корня репозитория:

```powershell
pnpm cloud:snapshot create apps/server/storage/turkish-flashcards.db backups/NEW-UNIQUE-DIRECTORY
pnpm cloud:snapshot verify backups/NEW-UNIQUE-DIRECTORY
pnpm cloud:restore-check backups/NEW-UNIQUE-DIRECTORY
pnpm cloud:test
```

Для сравнения статистики часовой пояс процесса должен совпадать с `sourceTimeZone`
снимка. В CI тестовые снимки создаются в собственном часовом поясе процесса.
Скрипт не вызывает `openDatabase()` для рабочей базы или её копии: миграции,
seed и автоматические исправления к ним не применяются.

Для Supabase CLI на машине с Docker:

```powershell
supabase start
supabase db reset
supabase test db
supabase db lint --level error
```

`db reset` относится только к локальному проекту; не добавляйте `--linked` для production.
Локальные Node-тесты используют PostgreSQL/PGlite с эмуляцией `auth.uid()`, настоящими
ролями и RLS. Они не доказывают доставку Auth-почты, проверку JWT платформой,
работу нескольких соединений или доступность облачных сервисов. CLI/pgTAP job
подготовлен, но в этой рабочей среде Docker/CLI отсутствуют и job здесь не запускался.

## Создание окружений

Пользователь подтвердил бесплатный закрытый пилот в Европе, адрес `pages.dev`,
чтение общего закрытого каталога зарегистрированными учащимися и назначение
старого прогресса одному владельцу. Платные услуги без отдельного решения не включать.

1. Создать Supabase **pilot** в доступном европейском регионе (предпочтительно Frankfurt).
   Production отделить другим проектом перед импортом настоящих данных. В preview
   использовать только pilot и синтетические данные из `supabase/seed.sql`.
2. Применить миграции по порядку через CLI/SQL Editor. Удалённый проект привязывать
   только после проверки его project ref. Локальный `config.toml` не настраивает
   автоматически Auth в уже созданном удалённом проекте.
3. В Auth отключить публичную регистрацию на пилоте, включить подтверждение email,
   задать Site URL будущего Pages-сайта и разрешить точный `/auth/callback` этого адреса.
   Для разработки — `http://127.0.0.1:5173/auth/callback`. Preview URL разрешать
   отдельно; не давать произвольным сайтам callback в production.
4. Настроить собственный SMTP перед проверкой внешних адресатов. Встроенный SMTP
   не считается готовой доставкой для учащихся. Создать/пригласить двух тестовых пользователей.
   PKCE-подтверждение/восстановление открывать в браузере, который начал запрос.
5. Скопировать `apps/web/.env.example` в `apps/web/.env.cloud.local` и указать URL
   pilot и его публичный publishable key. Значения `VITE_*` видны всем посетителям;
   secret/service-role, DB password и SMTP сюда не помещать.
6. Запустить `pnpm dev:cloud`, затем `pnpm build:cloud`. Для локального Supabase
   HTTP URL допустим только в dev; публикуемая сборка требует HTTPS Supabase URL.
7. Создать проект Cloudflare Pages: корень репозитория, команда `pnpm build:cloud`,
   output `apps/web/dist-cloud`, Node 22.18+; переменные Supabase задать отдельно
   для preview и production. Облачная сборка отличается от `build:static`.
8. Проверить пилот с выключенным домашним сервером, прямые `/study` и `/dictionary`,
   ширину телефона, вход двух аккаунтов, истечение сессии и сетевые сбои.
   Сравнить запросы браузера: персональные операции идут только в выбранный Supabase.

Документация: [Cloudflare build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/),
[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security),
[Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

## Подготовка импорта

UUID владельца берётся из **production Auth** после создания и подтверждения его
аккаунта. Email не заменяет UUID. Тестовый UUID из restore-check нельзя использовать
для настоящего владельца.

```powershell
# Только локальный dry-run, назначение не изменяется и не опрашивается:
pnpm cloud:import backups/FINAL-SNAPSHOT OWNER-AUTH-UUID
# Подготовить закрытый SQL; команда сама его не отправляет:
pnpm cloud:import backups/FINAL-SNAPSHOT OWNER-AUTH-UUID backups/FINAL-SNAPSHOT/import.sql
```

SQL применим только к пустому production-каталогу с уже существующим Auth-аккаунтом
владельца. Он сохраняет числовые ID и стабильную пару ключей источника/записи,
переносит старый прогресс только владельцу и сбрасывает sequence после явных ID.
Непустой каталог, чужой владелец, нарушенные связи или повторный снимок приводят
к откату всей транзакции. Offline dry-run проверяет только исходный снимок;
конфликты назначения проверяются при применении SQL.

Перед M8 обязательно закончить M6, проверить полный импорт/восстановление на обычном
PostgreSQL/Supabase, согласовать остановку записи и снять новый финальный snapshot.
Этот инструмент пока не реализует обратный перенос облачных ответов в SQLite.
