# Аккаунты и удалённый доступ: контракт R1

Статус: реализован отдельный модуль `apps/server/src/auth.ts` и его тесты. Он **не подключён** к `index.ts`, действующей SQLite-базе, HTTP Basic и туннелю. Ни один новый HTTP endpoint ниже пока не работает. Контракт предназначен для последующих R2/I2/C2.

## Что обнаружено в текущем сервере

- `hosting.ts` защищает интерфейс и весь API общим Basic-паролем. Только GET/HEAD `/healthz` обходят эту защиту.
- CORS сейчас разрешён только двум локальным origin при разработке. Запросы записи с другого сайта запрещены, включая `Sec-Fetch-Site: cross-site`.
- Production CSP рассчитана на ресурсы одного origin. Постоянный статический сайт будет иметь свою политику, которую надо согласовать с выбранным адресом API.
- Текущий список development CORS methods не содержит DELETE, хотя маршрут удаления существует.
- `index.ts` ограничивает JSON body 10 000 байт; сохранять это ограничение и проверку типов при добавлении auth-маршрутов.
- Внутри API пока нет пользователей и проверки ролей; данные повторений общие. Нельзя включить аккаунты только заменой Basic-пароля.

## Формат сессии

Публичный пользователь:

```json
{"id":1,"username":"owner","displayName":"Владелец","role":"owner"}
```

`id`: целое число, устойчивый ключ `users.id`, роли `owner` или `learner`. Username канонизируется: trim + lowercase; 3–64 ASCII символа, первый — латинская буква или цифра, далее также `.`, `_`, `-`. Display name — 1–80 Unicode символов без управляющих символов.

Пароль регистрации: минимум 12 Unicode символов, максимум 1024 UTF-8 байта. Не обрезать и не нормализовывать пароль на клиенте или сервере. На входе разрешены и короткие неверные пароли, чтобы вернуть единый ответ о неверных данных. Слишком большой ввод отклоняется до KDF.

Успешные вход и регистрация возвращают HTTP 200/201:

```json
{
  "token":"<непрозрачное случайное значение>",
  "expiresAt":"2026-11-02T12:00:00.000Z",
  "user":{"id":1,"username":"owner","displayName":"Владелец","role":"owner"}
}
```

Срок сессии — 12 часов, без неявного продления; `expiresAt` — ISO UTC. Клиент хранит bearer-токен в памяти и отправляет `Authorization: Bearer <token>`. После перезагрузки нужен вход. Токен не помещается в URL, localStorage, публичный кэш или журнал. Сервер хранит SHA-256 токена, сессия отзывается при выходе; отключённый пользователь не проходит проверку даже со старой сессией.

## Новые маршруты R2

| Метод и путь | Доступ | Запрос | Ответ |
| --- | --- | --- | --- |
| GET `/api/capabilities` | Без входа | — | 200, контракт ниже |
| POST `/api/auth/login` | Без входа, с лимитами | `{username,password}` | 200, сессия |
| POST `/api/auth/register` | Без входа, действительное приглашение, с лимитами | `{invitation,username,password,displayName}` | 201, сессия учащегося |
| GET `/api/auth/me` | Bearer | — | 200, `{user,expiresAt}` |
| POST `/api/auth/logout` | Bearer; идемпотентное завершение | `{}` | 200, `{revoked:true}`; в R2 допустимо не требовать живую сессию для уже отозванного токена |
| POST `/api/auth/invitations` | Владелец | `{}` | 201, `{invitation,expiresAt}` |

```json
{
  "apiVersion":1,
  "features":{
    "accounts":true,
    "invitationRegistration":true,
    "personalProgress":true,
    "idempotentReviews":true
  }
}
```

Возможности объявляются только после реальной интеграции соответствующей функции. До C2/C3 нельзя объявлять `personalProgress` и `idempotentReviews` как работающие. Клиент отвергает неподдерживаемую версию API; сетевой сбой не равен 401.

Приглашение — 32 случайных байта в base64url, срок 24 часа, роль всегда learner. Переданное клиентом поле `role` не может повысить права. Приглашение хранится только в виде SHA-256; создание пользователя, потребление приглашения и создание сессии фиксируются одной транзакцией. Ошибка/занятый username не расходует приглашение. Две конкурентные регистрации по одному приглашению создают ровно один аккаунт. Отключение создавшего приглашение владельца делает приглашение недействительным.

Пароли хранятся как `scrypt$32768$8$1$<16-byte salt hex>$<64-byte key hex>`. KDF выполняется асинхронно, транзакции SQLite не удерживаются во время ожидания. Проверка выполняется через `timingSafeEqual`. У неизвестного пользователя выполняется KDF той же стоимости. Параметры проверены по [официальной документации Node crypto](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

## Ошибки и лимиты

```json
{"error":"Войдите в аккаунт заново.","code":"UNAUTHORIZED"}
```

| HTTP | code | Значение |
| --- | --- | --- |
| 400 | INVALID_INPUT | Неверный формат или размер поля |
| 400 | INVALID_INVITATION | Нет действительного приглашения, оно истекло либо уже использовано |
| 401 | INVALID_CREDENTIALS | Одинаковые код и текст для неизвестного пользователя, неверного пароля и отключённого аккаунта |
| 401 | UNAUTHORIZED | Нет живой сессии |
| 403 | FORBIDDEN | Живая сессия без необходимых прав |
| 409 | USERNAME_TAKEN | Username занят при регистрации |
| 429 | RATE_LIMITED | Лимит; добавить заголовок `Retry-After` в секундах |
| 500 | INTERNAL_ERROR | Ошибка хранилища/формата сохранённого хеша; не выдавать за неверный пароль, не включать внутренние детали |

Модуль ограничивает попытки до дорогого KDF: 5 входов на username и 30 на доверенный client key за фиксированное окно 15 минут. Успешный вход сбрасывает username bucket, но не client bucket. Регистрация ограничена 10 попытками на client key за 15 минут. Лимиты хранятся в SQLite и переживают пересоздание AuthStore. Истёкшие buckets удаляются при следующей попытке.

`clientKey` обязателен для login/register и задаётся HTTP-адаптером, а не телом запроса. За туннелем все запросы могут иметь loopback socket address. В R2 надо определить доверенную конфигурацию прокси: никогда не принимать произвольный `X-Forwarded-For` как личность или как достоверный client key. При отсутствии доверенного адреса использовать общий bucket сервера (безопасно, но ограничивает всех посетителей вместе). Защиту от массовых параллельных KDF и общий лимит HTTP-запросов дополнить на границе API; лимиты модуля не заявляются полноценной DDoS-защитой.

## Передача агенту карточек: схема и порядок миграций

- `users.id INTEGER PRIMARY KEY AUTOINCREMENT`; один owner, learner без ограничений количества.
- `users`: `username`, `display_name`, `role`, `password_hash`, `created_at`, `disabled_at`. Все времена хранилища — целые миллисекунды Unix UTC.
- `auth_sessions`: `token_hash`, `user_id`, `created_at`, `expires_at`, `revoked_at`.
- `auth_invitations`: `token_hash`, `created_by`, `created_at`, `expires_at`, `consumed_at`, `consumed_by`.
- `auth_attempt_limits`: `bucket_hash`, `attempts`, `expires_at`.
- `auth_schema_migrations`: локальная история auth-схемы, сейчас версия 1; не менять глобальный SQLite user_version приложения.
- Миграция вызывается явно: `migrateAuth(database)`. Она не запускается при импорте модуля и создании `AuthStore`.
- После согласованного backup: основная схема → auth-схема → локальное создание владельца → C2 с переданным `owner.id` → включение защищённых HTTP-маршрутов. Окончательный порядок C2 должен учитывать существующие связи и обеспечивать атомарную миграцию прогресса.
- `new AuthStore(database)` никогда не открывает файл самостоятельно и не имеет default production path.

Начальное создание владельца выполняется отдельной доверенной локальной процедурой: оператор явно вводит username, display name и новый пароль через скрытый ввод. Будущий setup CLI не должен помещать пароль в командную строку или печатать его. Он вызывает `bootstrapOwner` только после проверки резервной копии и миграции. HTTP-маршрута bootstrap нет. Эта процедура ещё не подключена к скриптам запуска. Существующий общий Basic-пароль автоматически не становится паролем владельца.

## Что остаётся за R2/R3

- HTTP-адаптеры, runtime validation JSON и отображение AuthError в HTTP.
- C2/C3: индивидуальный прогресс, идемпотентность оценки и отмены; auth-модуль не реализует расписание.
- Совместимая схема Basic/Auth: публичные auth endpoints/capabilities не должны требовать Basic, остальные API требуют сессию; старые незащищённые пути должны исчезнуть без обхода через локальный origin.
- Точный allowlist сайта, CSP, ограничение параллельной KDF-нагрузки и настройки доверенного прокси.
- Setup CLI, инструкции резервного копирования, корректировка конфигурации запуска и реальная проверка через туннель на телефоне.
- Настройки окружения предполагаются `AUTH_ALLOWED_ORIGINS` (точные origins) и явная конфигурация доверенного proxy; имена окончательно фиксирует координатор. В R1 модуль не читает окружение и не меняет `.env.example`.

## Проверка R1

```powershell
node --disable-warning=ExperimentalWarning --test apps/server/src/auth.test.ts
```

Тесты используют только `new DatabaseSync(":memory:")`: явную повторяемую миграцию; bootstrap и хеши; неверные данные входа; expiry/revocation/disabled; права; одноразовость и конкурентное потребление приглашений; откат регистрации при ошибке создания сессии; лимиты и ошибки хранилища. Прямой импорт модуля не меняет действующий сервер.
