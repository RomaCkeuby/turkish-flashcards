# Агент 2: карточки, публичный пакет и прогресс

Сначала прочитать `agent-tasks/README.md` и `ROADMAP-HYBRID.md`. Выполнять C1 → C2 → C3. Не запускать дополнительные агенты автоматически.

## Цель

Подготовить независимую публичную подборку и браузерную колоду; затем сделать существующую SQLite-модель прогресса многопользовательской без потери текущих данных.

## Границы

Владение — по README. Основной файл: `apps/server/src/database.ts`. Не менять серверные маршруты `index.ts`, авторизацию и экраны. Новые сигнатуры API передавать агенту удалённого доступа. Новые типы и команды согласовать с координатором до интеграции.

## C1. Публичные данные и колода

- Использовать подготовленный источниковый пакет `apps/server/update-packages/current`, а не экспорт содержимого личной рабочей БД.
- Создать воспроизводимый генератор публичного JSON-пакета и manifest. Сохранить источники, лицензии и стабильные ключи, согласованные в общем контракте.
- Проверять формат, обязательные значения, дубли и контрольную сумму; не включать историю, прогресс, пользователей и личные исправления.
- Реализовать чистый браузерный модуль `apps/web/src/guestDeck.ts` без Node API: оба направления, фильтры, перемешивание, пустая выборка, завершение прохода и новый проход.
- Избежать перечитывания и фильтрации всего пакета при каждом перевороте. На текущем объёме не добавлять сложные индексы без измерений.
- Дать агенту интерфейса небольшую фикстуру и точный интерфейс модуля до завершения экспорта.

Приёмка: пакет собирается без доступа к рабочей БД; атрибуция сохранена; ключи не зависят от порядка строк; каждая подходящая карточка появляется ровно один раз за проход. Тесты проверяют это на контролируемом источнике случайности.

## C2. Отдельный прогресс пользователей

Вход: доверенный контекст пользователя и схема users от агента удалённого доступа. Порядок миграций согласовать до правок.

- Сначала исследовать все таблицы и запросы прогресса, журналов, отмен и статистики; составить список изменений.
- Работать на копии/отдельной тестовой БД. До производственной миграции подготовить способ согласованного backup с учётом WAL и проверку восстановления.
- Добавить принадлежность пользовательского состояния и необходимые уникальные ключи/индексы.
- Перенести текущую историю и расписание первому владельцу ровно один раз. Миграция транзакционная и повторно безопасная.
- Обновить очередь, детали карточек, дневную статистику, оценку и отмену. Не выводить персональные поля без конкретного пользователя.
- Новые пользователи начинают с чистого прогресса; общий каталог не дублировать для каждого пользователя.
- Учесть оба направления, отключение, удаление, восстановление, слияние и apply/rollback пакета. Слияние сохраняет корректное состояние отдельно для каждого пользователя.

Приёмка: минимум два тестовых пользователя; оценка/отмена одного не меняют очередь и статистику другого. Проверены миграция старой схемы, повтор миграции и восстановление копии.

## C3. Надёжная оценка и регрессии

- В одной транзакции сохранять оценку и результат операции по уникальному ключу пользователь + operationId.
- Повтор одинакового запроса возвращает прежний результат; конфликт содержимого по тому же ID отклоняется.
- Отмена принадлежит пользователю и не перезаписывает более новое состояние; согласовать блокировки/проверки с существующим механизмом.
- Обновления общей коллекции и их откат сохраняют прогресс всех пользователей и личные правки владельца.
- Передать сигнатуры и примеры вызовов агенту удалённого доступа. Порядок интеграции не должен оставлять старые неавторизованные пути записи.

Приёмка: потеря HTTP-ответа и повтор оценки не дублируют запись; разные пользователи могут независимо использовать одинаковый operationId; существующие регрессии обновлений и редактирования проходят.

## Передача

Отчёт: формат и местоположение пакета, алгоритм идентичности записей, команды сборки/проверки, новые сигнатуры SQLite, миграционный порядок, инструкции резервного копирования, результаты тестов. Рабочую базу не мигрировать в рамках подготовки кода.
